🔒 Penetration Test Report – VulnerableBank

Engagement Date: 11-06-2026
Prepared by: Ritesh Kumar Singh
Application: VulnerableBank – Banking Web Application
Environment: Isolated Docker Lab (Kali Linux + Docker Desktop)

📋 Executive Summary

A comprehensive penetration test was conducted against VulnerableBank, a purposely vulnerable banking web application. The engagement successfully identified 12+ high/critical severity vulnerabilities, including SQL Injection, IDOR, XSS, business logic flaws, unrestricted file upload, weak session management, and information disclosure. All attacks were performed in a contained lab environment.

Overall Risk Rating: 🔴 Critical (CVSS 9.8 average)

Key Findings:

  • SQL Injection in login form (no prepared statements)
  • IDOR allowing unauthorized account access
  • Negative amount transfer (business logic bypass)
  • Reflected XSS via error parameter
  • Unrestricted file upload (reverse‑shell possible)

🎯 Scope & Methodology

In-Scope Assets: Web Application (http://localhost:5001), PostgreSQL 15, APIs: /login, /transfer, /account/<id>, /profile, /admin

Testing Methodology (PTES & OWASP): Reconnaissance → Vulnerability Analysis → Exploitation → Post-Exploitation → Reporting

Tools Used: Kali Linux, Nmap, Burp Suite, Hydra, Nessus, OpenVAS, Veil, Wireshark

🔍 Detailed Findings

F‑01: SQL Injection in Login Form (Critical)

Location: /login – username field
Reproduction: Username: ' OR '1'='1' --, Password: anything. → Logged in as admin without password.

Remediation: Use parameterized queries / prepared statements.

F‑02: Insecure Direct Object Reference (IDOR) – High

Location: /account/<id>
Reproduction: Login as alice (password: hello), then access /account/3 → see Bob's account details.

Remediation: Implement server‑side access control; verify user_id matches session.

F‑03: Negative Amount Transfer (Business Logic Bypass) – Critical

Location: /transfer endpoint
Reproduction: Transfer amount -500 to same account → balance increases.

Remediation: Validate amount > 0 server‑side.

F‑04: Reflected XSS via error Parameter – Medium

Location: /error?message=...
Reproduction: http://localhost:5001/error?message=<script>alert('XSS')</script>

Remediation: Output encoding (escape user input).

F‑05: Unrestricted File Upload – High

Location: /profile (profile picture upload)
Reproduction: Upload shell.php → file stored in /static/uploads/

Remediation: Validate file type (MIME, magic bytes); store outside webroot; rename files.

F‑06: Weak Session Management – Medium

Location: Entire app
Issues: auth_token missing HttpOnly flag; JWT weak secret; no session regeneration.

Remediation: Set HttpOnly, Secure, SameSite flags; use strong secrets; regenerate session on login.

F‑07: Information Disclosure – Low

Location: Debug mode enabled (debug=True)
Reproduction: Trigger any unhandled exception – full traceback appears.

Remediation: Disable debug mode in production; implement custom error pages.

🔧 Remediation Roadmap

  • Short‑term (0‑2 days): Fix SQL injection, validate transfer amount, restrict file uploads.
  • Mid‑term (1 week): Implement access control, set HttpOnly/Secure flags, disable debug mode.
  • Long‑term (2‑4 weeks): CSRF tokens, rate limiting, CSP, regular security testing.
